## 0. 一句话需求

用户不用再真的掉下去走一遍 —— 在**放大 4 倍的小地图**上点几下（落点 → 途经点 → 回到主线），就能画出一条回正线；并且**掉下去只掉了一点点（5~15px）时，这条线也真的会被触发、真的能走完**。

---

## 1. 原始需求复述（需求方原话）

1. 选**方案 A：手绘回正线** —— 在录制器里用鼠标在小地图上点出「落点 → 途经点 → 回到主线」，自动生成 `route_home.png`，**不再要求他真的在游戏里掉下去一次再走回来**（现有流程依赖识别小地图黄点，实测只录到 6px 的一团，判废）。
2. 质疑：**「小地图这么小，你确定到时候能识别准确么」**（担心 268×187 上画不准）。
3. 主动补充的关键场景：**「回正线可能非常短，毕竟从一个很小的台子上掉下去，可能只需要轻轻一跳就上来了」**。

---

## 2. 产品目标（3 个，互相独立）

| # | 目标 | 可衡量标准 |
|---|------|-----------|
| G1 | **不掉下去也能补出回正线** | 从打开手绘面板到保存成功 ≤ 5 分钟 / 条；全程鼠标，不需要操作游戏角色 |
| G2 | **短掉落也能触发并走完回正** | 落点距主线 5~15px 的场景，引擎能进回正状态、能走完、能回主线；不出现「原地左右横跳」和「一进回正就被踢出来」 |
| G3 | **判废规则不再误杀合法短回正线，但仍拦得住真废线** | 一条 8px 长 + 1 个跳跃像素 + goal 的回正线 → 判定有效；当前 `废都南方工地/route_home.png`（20px 挤在 6px 里）→ 仍判定废线 |

## 3. 用户故事

1. **作为一个挂机用户**，我想在电脑上直接画出「掉下去之后怎么走回来」，这样我就不用为了录一条线故意跳下平台、还得祈祷小地图黄点能被识别到。
2. **作为一个挂机用户**，我希望画面放大一点再让我点，这样我看得清台子和主线的位置，不会因为小地图太小而点歪。
3. **作为一个挂机用户**，我希望「只掉了一小截、跳一下就能上来」这种情况也能自动回来，因为这种小台子掉落才是最常发生的。
4. **作为一个挂机用户**，我希望画错了能撤销/删掉一条重来，而且一条画废了不要把别的几条一起连坐。
5. **作为一个非程序员**，我希望哪里画得不对时，界面/日志直接用人话告诉我「哪里不对、该怎么改」，而不是甩一句「判为废线」。

## 4. 本次要解决的四个坑（每条需求都会回指这里）

### 坑 1：短掉落根本触发不了回正（**核心**）
- 位置：`src/engine/MapleStoryAutoLevelUp.py:1870` `update_cmd_by_route`
- 现状：只有「主线 + 回正线都找不到像素」才置 `is_using_home_route = True`。
- 搜索半径 `search_range=10`、失联救援 `rescue_range=40`（曼哈顿距离）。
- 后果：小台子掉下去，落点离主线只有 5~15px，引擎**透过地板还能"看见"主线** → 永远不进回正状态 → 回正线是死代码，角色在台子下面跟着主线像素左右横跳。

### 坑 2：判废规则误杀合法短回正线
- 位置：`validate_route_image`（≈305-342 行），三条任一不满足即废：① 色码像素 < 20；② 没有 goal；③ bbox 跨度 < 10px。
- 后果：一条 8px 长 + 1 个跳跃像素的合法回正线会被 ①③ 直接扔掉。
- 实测（我复核过）：`minimaps/废都南方工地/route_home.png` = **20 个色码像素，bbox x[96,102] y[120,126]，跨度 6px** → 命中 ③ 被判废，日志原文与交接一致。

### 坑 3：`home_return_range: 20` 抢跑
- 位置：`try_return_to_mainline`（1666 行），每帧在曼哈顿 20px 内找主线像素，找到就「已回主线」→ 立刻退出回正。
- 后果：落点离主线 < 20px 时，一进回正就被掐掉 → 角色继续卡在台子下面。

### 坑 4（本次新增发现）：回正线的**退出**只认 goal 像素，短线上必然失效
- 位置：`check_reach_goal`（2048 行）→ `reached = (cmd_action == "goal") or self._near_seg_goal()`；而 `_near_seg_goal`（1759 行）**在回正状态下直接 return False**（它是给主线分段用的）。
- 后果一：回正期间只剩「踩到 goal 圆点（半径 2px）」这一条退出路径，而**角色一帧能走十几像素** → 8px 的回正线会被一帧跨过 → 永远出不了回正状态。
- 后果二（更隐蔽）：`search_range=10` **大于整条回正线的长度** → 角色站在落点时，最近的回正线像素可能**就是 goal**（黄）→ 一进回正就被判「走完了」，原地退出。
- 结论：回正的**进入**和**退出**都必须加「最小驻留」保护，否则短线两种死法（进不去 / 一进就出）占全。

## 5. 需求池

> 优先级：P0 = 必须有（不做则 v0.9 不成立）；P1 = 应该有；P2 = 锦上添花。
> 每条都标了「解决哪个坑」和「验收标准」。

### P0-1　手绘回正线：放大画布 + 鼠标点选（解决：方案 A 本体、需求方疑问 2）
- 在录制流程里新增一步「手绘回正线」（入口见 P0-2）。
- 画布：以 `minimaps/<图>/map.png` 为底图，**叠加显示已录好的主线**（route1/route2…）和**已有的回正线**，让用户一眼看清「主线在哪、坑在哪」。
- 缩放：**默认 4 倍**（268×187 → 1072×748），窗口超出屏幕时自动降到能完整显示的最大整数倍（≥3 倍），支持滚轮 3~6 倍微调。
- 用户在放大图上依次点击：
  - **第 1 点 = 落点**（自动标记为「落点」，是后面触发回正的锚）；
  - 中间点 = 途经点（可 0 个）；
  - **最后点 = 回到主线的接驳点**（自动盖上 goal 标记）。
- 相邻两点之间按方向自动上色（沿用录制器现有着色规则：右=蓝、左=红、上=灰、下=浅黄），线宽 1px，落点/终点画 2px 圆点。
- **坐标换算**：显示的屏幕坐标 ÷ 缩放倍数 → 原图坐标（四舍五入），并 clamp 到 [0, W-1] / [0, H-1]。
- **验收标准**：
  1. 在 4 倍画布上点 (400, 300) → 原图落点为 (100, 75)，误差 ≤ 1 原图像素；
  2. 点出 3 个点保存后，用现有像素统计脚本能读出 3 段线 + 1 个 goal；
  3. 放大图上点哪、保存的 `route_home.png` 上就画在哪（像素级一致，可用裁剪对比验证）。

### P0-2　入口：不用先掉下去（解决：需求方原话 1）
- 主界面地图列表 / 录制面板里新增按钮 **「手绘回正线（推荐）」**，与现有的「补录回正线」并列。
- 点它 → 直接打开手绘画布（不需要启动游戏抓帧、不需要角色定位、不需要人在游戏里）。
- 原有的「先掉下去再走回来」流程**保留但不主推**（收进「老办法（要真掉一次）」），避免已习惯的用户找不到。
- **验收标准**：游戏未启动时，手绘入口可用、能保存；保存后 `minimaps/<图>/route_home.png` 被更新。

### P0-3　落点锚：存坐标 + 落点触发进回正（解决：坑 1）
- 手绘的第 1 个点 = **落点锚**，需要持久化坐标（存哪儿见「待确认 Q2」，默认方案：sidecar `minimaps/<图>/route_home.json`，结构：`[{id, anchor:[x,y], goal:[x,y], n_points, created}]`）。
- 引擎新增触发条件（与现有「看不见主线」**并存，取或**）：
  > 角色位置到任一落点锚的曼哈顿距离 ≤ R（`home_anchor_radius`）→ **无条件进入回正状态**，不管此刻看不看得见主线。
- **R 不能是固定值**：手绘保存时算出 `D = 落点锚到最近主线像素的曼哈顿距离`，落点触发半径取 `R = min(R_default, D - 3)`，下限 3px。
  - 理由：R ≥ D 的话，角色在主线上正常巡逻经过落点上方时会被误判成「掉下去了」→ 比不回正更糟。
  - 保存时把这条线的 `D` 和 `R` 一起写进 json，并在界面/日志显示。
- **验收标准**：
  1. 构造一条落点距主线 8px 的手绘回正线（R 自动收紧为 5）→ 模拟角色站在落点 → 引擎进入回正状态（日志有「[回正] 触发落点锚」）；
  2. 模拟角色在主线上正常巡逻、路径经过落点上方 6px 处 → **不**进入回正状态；
  3. 主线像素在 10px 内可见（坑 1 场景）→ 仍然进入回正状态。

### P0-4　回正期间的最小驻留：屏蔽抢跑（解决：坑 3 + 坑 4）
- 进入回正状态时记录 `t_home_enter` 与进入时的位置；在**下面两个条件都没满足之前**，屏蔽一切「退出回正」的判定（既屏蔽 `try_return_to_mainline` 的 20px 抢跑，也屏蔽 `check_reach_goal` 的 goal 判定）：
  - ① 角色已**离开落点锚**（距进入时位置 ≥ `home_min_leave`，默认 6px）**或**已在回正状态 ≥ `home_min_frames`（默认 15 帧 ≈ 0.5s）—— 两者取或，防止「跳一下就上来」时角色位移不到 6px 而卡在回正里；
  - ②（兜底）回正状态超过 `home_timeout`（默认 8s）仍未回主线 → **退出回正、交还给打怪逻辑**（沿用项目既有纪律：「加开关必须加出口」，见 1877-1899 行的注释）。
- 解除屏蔽后，「真的回主线了」的判据**收紧到 `search_range`（10px）**，不再用 `home_return_range`（20px）——20px 是给长回正线留的，短掉落场景下就是它抢跑。
- **验收标准**：
  1. 8px 回正线 + 角色站落点 → 进入回正后**至少 15 帧内不退出**；
  2. 角色一帧位移 12px 跨过 goal → 仍能由「离开落点锚 + 靠近主线 ≤10px」正常退出回正，不会永久卡在回正里；
  3. 模拟回正线接不上 → 8s 后自动退出回正并恢复打怪（日志有对应告警）。

### P0-5　回正线专用判废规则（解决：坑 2）
- 回正线**不再复用**主线的三条判废（不查 20 像素、不查 10px 跨度），改用下面这套；**判废粒度改为「每条回正线」而不是整张图** —— 一条废了只禁用那一条（从加载的图里抹掉它的像素 + 删掉它的锚点），同图其他回正线照常生效。
- 新判据（全部满足才启用）：
  1. **有 goal**（沿用，合理）；
  2. **有落点锚**（json 里有对应条目；走降级路径时能从 PNG 反推，见 P2-1）；
  3. **落点锚 → goal 的曼哈顿距离 ≥ `home_min_return_span`（默认 5px）** ← 这是「合法短回正线」与「原地起头原地收尾废线」的分水岭：废线里 goal 就压在起点上（距离 0~3px），合法短线哪怕只跳一下，起点（台子下）和终点（台子上）也必然分开 ≥5px；
  4. **至少含 1 个位移动作像素**（left/right/up/down/jump 任一）—— 只有 goal 的等于没画；
  5. **落点锚到最近主线像素的距离 D ≥ `home_anchor_min_clearance`（默认 6px）** ← 落点画在主线上 = 这条线没有意义（当前那条废线 D≈0，会命中这条）。
- 只警告不判废：`goal` 到最近主线像素 > 15px（接驳点画偏了，回去了也接不上主线）。
- **验收标准**：
  1. 现网 `废都南方工地/route_home.png`（20px / 跨度 6px / D≈0）→ **仍判废**，且日志给出人话原因「这条回正线的起点就画在主线上（离主线 0px），等于没画 —— 请把落点点在台子下面」；
  2. 一条 8px 长 + 1 个跳跃像素 + goal 的手绘线 → **判有效并加载**；
  3. 一张图里有 2 条回正线、其中 1 条废 → 只禁用那 1 条，另 1 条正常运行（引擎日志分别列出）。

### P0-6　支持「跳一下就上来」（解决：需求方原话 3）
- 手绘时必须能放跳跃点。色码表已支持，只需要在 UI 上暴露：
  - 洋红 `255,0,255` = 原地跳；橙 `255,127,0` = 左跳；青 `0,255,255` = 右跳；青绿 `127,255,0` = 下+跳；粉 `255,0,127` / 紫 `127,0,255` = 上/下瞬移（绳索/传送，可选）。
- UI 表达（推荐，见待确认 Q3）：画布上方一排「这一段怎么走：→ 走 / ⤴ 跳 / ↑ 上（爬绳）」，**先选动作再点下一个点**；已画的点在画布上用不同颜色区分，选中某点可改动作。
- 最短形态必须能成立：**落点(1px) + 1 个跳跃像素 + goal** 就算一条合法回正线。
- **验收标准**：画一条「落点 → 洋红原地跳 → goal（主线上）」三点线 → 判有效；引擎模拟角色站落点 → 发出 jump 指令 → 到达 goal → 退出回正。

### P0-7　自检与回归（解决：可维护性）
- `python -m tools.verify_navigation`（现 19 项）与 `python -m tools.verify_load_config`（现 4 项）**必须全过**，并新增用例：
  1. 落点锚触发（含「主线可见时也要触发」的反向用例）；
  2. 主线上巡逻不误触发（R < D 的边界用例）；
  3. 短回正线判废规则：合法短线通过 / 6px 团废线拦截；
  4. 回正最小驻留 + 8s 超时出口；
  5. 4 倍画布坐标换算（点 (400,300) → (100,75)）。
- 引擎侧新增代码**必须复用** `load_image`（内部 `cv2.imdecode(np.fromfile(...))`）—— 中文路径下 `cv2.imread` 会静默失败，这是本项目已踩过的坑。
- **验收标准**：`verify_navigation` 项数 ≥ 24、`verify_load_config` ≥ 4，全绿；中文路径地图（如 `废都南方工地`）全部用例通过。

### P1-1　手绘面板的编辑能力
- 撤销上一个点（Ctrl+Z / 按钮）、清空重画、删除某一条已有回正线（从 json 和 PNG 上一起删）。
- 已有回正线在面板上以列表展示：`#1 落点(98,130) → 主线(102,121)，3 点，跳 1 次`，可选中高亮、可删。
- 落点太靠近主线（D < 6px）时**实时红色提示**：「这里离主线太近了，请点在台子下面一点的落点上」。
- 验收：撤销后 PNG 上的像素同步消失；删一条不影响另一条。

### P1-2　加载期体检报告（人话）
- 引擎加载回正线时，把每条线的「落点坐标 / 离主线 D px / 触发半径 R px / 点数 / 是否含跳跃」打成一行中文日志。
- 判废/告警一律写成「症状 + 怎么改」，禁止只写「判为废线」。
- 验收：非程序员用户能只看日志知道下一步该做什么。

### P1-3　方向侧判据（可选增强，用来放宽 R）
- 若落点锚半径被 D 压得太小（R < 4px，定位误差可能吃掉），增加几何判据：仅当角色位于**落点背离主线的那一侧**（(player-anchor)·(anchor−nearest_mainline) ≥ 0）时才触发，允许 R 放大到 D。
- 验收：在 D=8 的线上，R 可从 5 放宽到 8 且不误触发主线上巡逻。

### P1-4　回正期间的打怪策略保持现状
- 沿用 v0.8「回正期间不打怪」。短回正只跳一下，无感；长回正时避免打断跳跃。
- 验收：回正状态下不发出 attack。

### P2-1　无 json 时的降级
- 用户只拷了 `route_home.png` 没拷 json → 从 PNG 的连通域里反推锚点（取每条连通域中距主线最远的像素作为落点锚），功能降级但不至于失效。
- 验收：删掉 json 后引擎仍能加载并触发回正（日志提示「未找到落点锚文件，已自动推断」）。

### P2-2　手绘主线（复用同一套 UI）
- 同一套放大画布 + 点选，用来手绘 `route1.png` / `route2.png`。**本期不做**，先把回正线跑通。

### P2-3　回正线预览动画
- 面板上「试跑一下」：按顺序高亮这条线的像素，让用户提前看清引擎会怎么走。

```
├───────────────────────────────────────────────────────────────┤
│ [撤销上一点]  [清空重画]      [取消]  [保存这条回正线]          │
└───────────────────────────────────────────────────────────────┘
```

**用户在界面上看到什么、点哪里、发生什么：**

| 用户动作 | 界面反应 |
|---------|---------|
| 打开面板 | 看到放大 4 倍的小地图，已录好的主线用原来的红/蓝线画着，一眼能看出台子和坑在哪 |
| 「这一段怎么走」里选「跳一下」 | 按钮高亮；接下来点的那一段会画成跳跃色（洋红/橙/青），画布上显示为带小箭头的线 |
| 在图上点第 1 下 | 出现一个**靶心**图标 + 文字「落点」；底部实时显示这个点离主线多少 px。点得太靠近主线 → 红字提醒「这里离主线太近了，请点在台子下面一点的落点上」 |
| 继续点第 2、3 下 | 每点一下，和上一个点之间自动连一条彩色线（右=蓝、左=红、上=灰、跳=对应跳跃色） |
| 点「保存这条回正线」 | 最后那个点自动盖上黄色终点标记 → 存进 `route_home.png`（叠加到已有的回正线上）+ 记下落点坐标；窗口提示「已保存，这条线离主线 9px，触发半径 6px」 |
| 「我再画一条」 | 画布清空，可以画另一个坑的回正线；已有的那条仍在图上以半透明显示 |
| 点错一下 | 「撤销上一点」；全乱了就「清空重画」 |
| 想删掉以前画的某条 | 底部列表选中那条 → 删除（只删这一条，不影响其他条） |

## 7. 给需求方的正面答复：小地图这么小，画得准吗？

**结论：画得准不是主要风险，「能不能触发」才是。**（数据均来自本机实测）

| 需求方担心 | 实测事实 | 结论 |
|---------|---------|------|
| 268×187 太小，点不准 | 手绘画布默认**放大 4 倍**，1 个原图像素 = 4 个屏幕像素；鼠标点击误差 ±1 屏幕像素 = **±0.25 原图像素** | 可忽略 |
| 点歪了引擎就接不上 | 引擎在角色周围 **±10px（search_range）** 的带里找路线像素，失联时放宽到 **±40px**；而**主线本身跨度才 12px**（route1 bbox x[94,106] y[120,124]，route2 x[92,104] y[120,124]，各 21 个像素） | 10px 的搜索带相对 12px 的主线**是很宽的一条带**，点歪 2~3px 完全不影响 |
| 那到底风险在哪 | 在于**落点离主线只有 5~15px** —— 引擎透过地板「看得见」主线，于是**根本不进回正状态**（坑 1），以及 20px 的「已回主线」判定会立刻把回正掐掉（坑 3） | 本 PRD 的 P0-3 / P0-4 / P0-5 就是专门解决这个 |

一句话：**图小不是问题，「掉落太短、引擎察觉不到」才是问题** —— 本次需求 80% 的工作量在这里。

## 8. 待确认问题（需需求方拍板）

| # | 问题 | 我的建议 | 影响 |
|---|------|---------|------|
| Q1 | **落点锚触发半径 R 取多少？** 建议默认 8px，并按 `R = min(8, D-3)` 自动收紧（D = 落点到主线距离），下限 3px | 采建议；需要实测一次小地图定位误差（黄点 vs 名字标签）来定下限 | 太小触发不到，太大误触发主线巡逻 |
| Q2 | **落点锚存哪儿？** ① sidecar `route_home.json`（好读好改，但用户拷图时可能漏拷）；② 在 PNG 上用一种专用色码标记落点（单文件，但可能被色码/掩码逻辑误读） | **选 ①**，同时做 P2-1 降级（缺 json 时从 PNG 反推） | 影响数据可靠性与用户拷贝习惯 |
| Q3 | **跳跃动作在 UI 上怎么表达？** ① 先选动作再点下一个点（一排单选）；② 点完再右键切换这一段；③ 点完弹出小菜单 | **选 ①**，最不容易点错，非程序员一眼懂 | 影响手绘效率与误操作率 |
| Q4 | **回正最小驻留取多少？** 建议「离开落点 ≥6px **或** 已回正 ≥15 帧」二者取或 | 采建议 | 太小 = 一进就出；太大 = 卡在回正里 |
| Q5 | **回正超时出口取多少秒？** 建议 8s（< watchdog timeout 10s） | 采建议 | 接不上时多快放弃回正、回去打怪 |
| Q6 | **「真的回主线了」的判据从 20px 收到 10px，是否接受？** 长回正线（几十 px）场景下可能要多走一段才判定回主线 | 接受；若长线场景有反馈再单独给长线放宽 | 影响长回正线的收尾手感 |
| Q7 | **一张图里多条回正线怎么管理？** 是否需要命名/备注（如「左边坑」「右边坑」）、是否需要限制两条落点的最小间距（避免互相抢触发） | 建议：落点间距 < 2R 时保存时警告（不阻断） | 影响多坑地图的可用性 |
| Q8 | **是否保留老的「真掉一次再走回来」入口？** | 建议保留为「老办法」，但主推手绘 | 影响界面复杂度 |
| Q9 | **回正期间要不要允许打怪？** 现状是不打 | 建议维持不打（避免打断跳跃）；若长回正线场景被怪打断再议 | 影响长回正线的生存率 |
| Q10 | **是否需要连主线也支持手绘？**（复用同一套 UI，P2-2） | 本期不做，等回正线验证通过再说 | 影响本期工期 |
